# API для подключения frontend

Локальная база URL: `http://localhost:8080`. JSON-запросы отправлять с
`Content-Type: application/json`. По умолчанию CORS разрешает
`http://localhost:3000`; другой origin задаётся через `CORS_ORIGIN`.
Авторизации в MVP нет, роль и команда выбираются в интерфейсе.

## Основной сценарий

1. `POST /api/tasks` с `{"initial_description":"Заказы кафе ведём вручную"}`.
   Ответ `201`: объект задачи со статусом `draft`. Сохранить его `id`.
2. `POST /api/tasks/clarify` с `{"description":"Заказы кафе ведём вручную"}`.
   Ответ `200`: `questions` — массив `{field, question}`, `mode` —
   `mock`, `provider` или `fallback`; при fallback возможен `fallback_reason`.
3. `POST /api/tasks/generate`:

   ```json
   {
     "description": "Заказы кафе ведём вручную",
     "answers": [{"field": "need", "answer": "Сократить ручной ввод"}]
   }
   ```

   Ответ `200`: `{card, readiness, mode, fallback_reason?}`.
   AI-запросы ничего не сохраняют в БД.
4. `PUT /api/tasks/{id}`: отправить **только `card`**, затем пользовательские
   изменения в том же формате. Ответ `200`: сохранённая задача с новым скорингом.
5. `POST /api/tasks/{id}/confirm` без тела: `200`, задача `confirmed`.
6. `POST /api/tasks/{id}/publish` без тела: `200`, задача `published`.
7. `GET /api/tasks` возвращает каталог опубликованных задач.
8. `GET /api/teams`, выбрать `id` команды; отправить отклик и принять/отклонить его
   через маршруты ниже.

Нулевой readiness не запрещает подтверждение, публикацию и отклики.
Публикация без подтверждения и повторные переходы возвращают `409`.
Это API-сценарий; автоматический тест не проверяет работу браузерного интерфейса.
Текущий frontend сначала вызывает clarify/generate, затем создаёт черновик и
сохраняет карточку. Создание черновика до AI не обязательно.

Для предварительного пересчёта: `POST /api/tasks/score`, тело — карточка
без обёртки. Ответ `200` — `scoring.Result` (формат ниже), без записи в БД
и без вызова LLM. При подтверждении backend заново считает оценку из
актуальной сохранённой карточки под блокировкой строки в транзакции.

## Карточка и задача

Все 11 полей карточки имеют тип `string | null`:

```json
{
  "title": "Форма заказа кафе",
  "topic": "Автоматизация",
  "context": "Заказы ведём вручную",
  "need": "Сократить ручной ввод",
  "users": "Администраторы кафе",
  "data": null,
  "constraints": null,
  "expected_result": "Прототип формы заказа",
  "success_criteria": "Оформление заказа за минуту",
  "contact": null,
  "interaction_format": null
}
```

`PUT` заменяет всю карточку: пропущенное поле очищается, как и `null`.
Не отправлять весь объект задачи: неизвестные поля отклоняются.
Для чтения одной задачи: `GET /api/tasks/{id}`, ответ `200`.

Объект задачи содержит поля карточки **на верхнем уровне**, а также:

- `id` — число; `initial_description` — строка или `null`;
- `clarification` — JSON, по умолчанию `{"questions":[],"answers":[]}`;
- `status` — `draft | confirmed | published`;
- `readiness_score` — число 0–100;
- `readiness_level` — `draft | workable | ready | priority`;
- `readiness_breakdown` — после расчёта массив `{name, points, max_points}`;
  у новой задачи/демоданных может быть `{}`;
- `missing_information` — массив названий отсутствующих полей;
- `suggestions` — массив строк;
- `confirmed_at`, `published_at` — дата-время или `null`;
- `created_at`, `updated_at` — дата-время в формате RFC 3339.

В ответе генерации `readiness` имеет **другой формат**:
`{score, level, breakdown, missing_fields, suggestions}`.
`level` там `Draft | Workable | Ready | Priority`, а `suggestions` —
массив `{field, text}`. Не смешивать этот объект с сохранённой задачей.
Подробности AI и скоринга: [AI_SCORING.md](AI_SCORING.md).

## Каталог

`GET /api/tasks?topic=Автоматизация&readiness_level=ready&sort=readiness_desc`

Ответ `200`: массив задач без обёртки, пустой результат — `[]`.
Все параметры необязательны: `topic` — точное совпадение;
`readiness_level` — одно из четырёх значений в нижнем регистре;
`sort` — `readiness_desc` (по умолчанию) или `readiness_asc`.
`readiness_level=draft` означает низкую оценку **опубликованной** задачи,
а не черновики. Пагинации нет.

Для раздела бизнеса: `GET /api/tasks?scope=all` возвращает задачи всех статусов,
включая черновики, новые первыми. Фильтры темы и уровня сохраняются, но сортировка
при `scope=all` всегда по времени создания. Другие непустые значения `scope`
возвращают `400`. Это общий список для демо, не список задач авторизованного владельца.

## Команды и отклики

`GET /api/teams` → `200`, массив объектов
`{id, name, interests, skills, technologies, created_at, updated_at}`.
Интересы, навыки и технологии — массивы строк. Не фиксировать seed ID во frontend.

`POST /api/tasks/{id}/proposals`:

```json
{
  "team_id": 1,
  "solution_idea": "Сделаем форму заказа",
  "plan": "Прототип, проверка с кафе, доработка",
  "timeline": "2 недели",
  "prototype_url": null
}
```

Использовать реальный `team_id` из списка. Первые четыре поля обязательны;
`prototype_url` необязателен. Ответ `201`: отклик со статусом `pending`.
Отклик содержит отправленные поля и `id`, `task_id`, `team_name`, `status`,
`created_at`, `updated_at`.

`GET /api/tasks/{id}/proposals` → `200`, массив откликов, новые первыми.

`GET /api/proposals` → `200`, общий массив откликов, новые первыми.
Frontend фильтрует его по выбранному `team_id`; серверной авторизации здесь нет.

`PATCH /api/proposals/{id}` с `{"status":"accepted"}` или
`{"status":"rejected"}` → `200`, обновлённый отклик.
Можно принять несколько команд; решение по одному отклику не меняет остальные.
Текущая реализация также допускает изменение уже принятого решения.

## Ошибки и ограничения

Обработчики API возвращают ошибки в формате:

```json
{"error":{"code":"task_not_published","message":"proposals are allowed only for published tasks"}}
```

- `400` — неверный JSON, ID, поля, фильтры или статус решения;
- `404` — `task_not_found`, `team_not_found`, `proposal_not_found`;
- `409` — недопустимый переход задачи или `task_not_published`;
- `500` — внутренняя ошибка; не считать операцию успешной.

Тело JSON ограничено 1 MiB; превышение в CRUD даёт `400`, в AI и `/score` — `413`.
AI-специфичные ошибки описаны в [AI_SCORING.md](AI_SCORING.md).
Вместо JSON-объекта нельзя отправлять `null` или массив.

Важные текущие ограничения: `PUT` не сбрасывает подтверждение/публикацию;
история AI-вопросов и ответов не сохраняется этими маршрутами;
права владельца и реальная авторизация не проверяются.
Frontend должен явно управлять шагами сценария и хранить ответы до генерации.
