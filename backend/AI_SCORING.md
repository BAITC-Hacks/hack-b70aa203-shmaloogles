# AI и readiness scoring: подключение

Общий контракт — `internal/taskcard.Card`: 11 полей `*string`, JSON `string | null`.
Все ключи присутствуют, `nil` означает отсутствие сведений. Поля: `title`, `topic`,
`context`, `need`, `users`, `data`, `constraints`, `expected_result`,
`success_criteria`, `contact`, `interaction_format`. Это вход/выход AI и скоринга,
не модель БД: ID, статус, подтверждение и сохранение принадлежат основному API.
Другой модели карточки в репозитории на момент реализации не было.

## Вызовы из основного API

При старте один раз вызвать `service, err := ai.FromEnv()` и проверить ошибку.
Сервис можно использовать из нескольких обработчиков одновременно.

```go
// В POST /api/tasks/clarify: JSON {"description":"..."}.
result, err := service.Clarify(r.Context(), description)
// result: {"questions":[{"field":"need","question":"..."}, ...], "mode":"..."}

// В POST /api/tasks/generate: ai.GenerateInput.
result, err := service.Generate(r.Context(), ai.GenerateInput{
    Description: description,
    Answers: []ai.Answer{{Field: "need", Answer: "Сократить ручной ввод"}},
})
// result: {"card":{...}, "mode":"...", "fallback_reason":"..." (при fallback)}

// Предварительная оценка для редактируемой карточки:
preview := scoring.Calculate(result.Card)
// После ручного подтверждения изменений основной API повторяет Calculate
// на фактически подтверждённой карточке и сохраняет результат вместе с ней.
```

Импорты: `github.com/shmaloogles/business-task-platform/backend/internal/ai`,
`.../internal/scoring`, `.../internal/taskcard`.
Методы не сохраняют карточку, не подтверждают и не публикуют её.
Маршруты пока не подключены: отдельные HTTP-обработчики не нужны для этих пакетов.
Основному API нужно декодировать и проверить HTTP-вход, ограничить тело запроса,
вызвать методы и вернуть JSON. Не продолжать обработку результата при `err != nil`.

Ошибки проверять через `errors.Is`: `ai.ErrInput` → 400,
`ai.ErrResponse`/`ai.ErrProvider` → 502, `context.DeadlineExceeded` → 504.
При отмене родительского контекста прекращать обработку; fallback не вызывается.
Описание обязательно, до 20000 байт; ответы — уникальные известные поля,
до 20000 байт каждый. Пустой ответ разрешён и означает неизвестное значение.

## Настройки и режимы

Без настроек работает **детерминированная заглушка** (`mode: mock`). Она задаёт
10 фиксированных вопросов по полям, кладёт описание целиком в `context`, переносит
ответы в соответствующие поля, остальные оставляет `null`. Она не анализирует смысл
описания и может повторно спросить об уже упомянутом факте. Не показывать её как LLM.

Реальный провайдер — изолированный REST-клиент Gemini, без SDK и новых зависимостей.
Контракт сверялся с [официальным generateContent API](https://ai.google.dev/api/generate-content).
Переменные окружения:

| Переменная | Значение |
| --- | --- |
| `AI_MODE` | `mock` (по умолчанию) или `gemini` |
| `AI_API_KEY` | Ключ, обязателен в режиме `gemini`; хранить только в окружении |
| `AI_MODEL` | Доступный вашему аккаунту ID модели с поддержкой JSON Schema; обязателен |
| `AI_BASE_URL` | По умолчанию `https://generativelanguage.googleapis.com/v1beta` |
| `AI_TIMEOUT` | Go duration, например `20s` (по умолчанию) |
| `AI_FALLBACK` | `false` по умолчанию; `true` включает заглушку при сбое реального AI |

Fallback возвращает `mode: fallback` и причину `timeout`, `provider_error` или
`invalid_response`. UI должен явно показать переход на заглушку. Ошибка конфигурации
не включает fallback. Сетевых повторов нет. HTTP-редиректы запрещены, ответ ограничен
1 МиБ; ключ передаётся заголовком, тела ошибок провайдера не выходят наружу.
Для замены провайдера реализовать маленький интерфейс `ai.Provider` и вызвать
`ai.New(provider, timeout, fallback)`. Провайдер обязан соблюдать переданный контекст.

Промпты находятся в `internal/ai/prompts/` и встроены через `go:embed`.
JSON Schema формируется в `validation.go` и передаётся провайдеру. Локальная проверка
независима от провайдера: JSON, типы, все ключи, отсутствие неизвестных/дублированных
ключей, 3–11 непустых разных вопросов по разным известным полям. Пустые строки
карточки нормализуются в `null`. Некорректный ответ не возвращается вызывающему коду.

Генерация намеренно extractive: значение — дословный фрагмент описания либо полный
ответ именно на это поле. Явный ответ имеет приоритет; пустой ответ даёт `null`.
Выдуманные значения и пропущенные непустые ответы отклоняются. Перефразирование
не поддерживается. Проверка происхождения текста не доказывает правильность его
отнесения к полю или сохранения смысла: карточку должен проверить человек.
Уместность вопросов обеспечивается промптом, структурная валидация её не доказывает.

## Правила скоринга

`scoring.Calculate(card)` — чистая функция, без LLM, БД и проверки подтверждения.
Результат: `score`, `level`, `breakdown` (name/points/max_points), `missing_fields`,
`suggestions` (field/text). Порядок стабилен, пустые списки сериализуются как `[]`.

| Категория | Начисление |
| --- | --- |
| Контекст и потребность | `context` 10 + `need` 10 |
| Данные | `data` 20 |
| Результат | `expected_result` 15 |
| Критерии успеха | `success_criteria` 15 |
| Ограничения | `constraints` 10 |
| Пользователи | `users` 10 |
| Связь с бизнесом | `contact` 5 + `interaction_format` 5 |

Заполненное поле — ненулевой указатель на строку, непустую после `strings.TrimSpace`.
Для одиночных полей частичных баллов нет; для составных категорий суммируются доли.
Содержательность, измеримость, правдивость, слова вроде «не знаю» алгоритм не оценивает:
любая непустая строка даёт баллы. Неизвестное нужно передавать `null`, не заглушкой текста.
`title` и `topic` не влияют на балл, но отсутствие отражается в подсказках.
Уровни: 0–39 `Draft`, 40–69 `Workable`, 70–89 `Ready`, 90–100 `Priority`.
Низкий балл не ограничивает публикацию и отклики. До подтверждения показывать балл
как предварительный; подтверждение и сохранение итогового балла выполняет основной API.

## Проверка и ограничения интеграции

Из `backend`: `go test ./...`, `go vet ./...`, `go build ./...`.
Тесты без ключей и сети: используется подставной провайдер и HTTP-транспорт в памяти.
Примеры входа/выхода в `internal/ai/testdata/`; пример генерации проверяется тестом,
даёт 60 (`Workable`). Без ответов тот же mock даёт 10, после заполнения всех
оцениваемых полей — 100. Примеры не являются набором seed-данных БД.
Пример `clarify-output.json` — образец ожидаемого ответа реального режима,
проверяемый подставным провайдером, а не запись живого вызова модели.

Реальный вызов платного/внешнего API без ключа не проверен. Основной API и frontend
должны ещё подключить методы; сквозная работа всего MVP здесь не заявляется.
`docs/MVP.md`, указанный в AGENTS.md, отсутствует: использованы локальное исходное
`ТЗ` и `docs/SPEC.md`. Баллы командам за прогресс упомянуты в исходном сценарии,
но исключены из текущего scope; в эту часть не входят. Баллы задачи после
подтверждения из исходного ТЗ учтены разделением предварительной оценки и сохранения.
